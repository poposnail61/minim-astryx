# Minim implementation plan

## Status and evidence

This is a tracking document, not a completion report. The repository starts from `facebook/astryx` commit `d6fd8d45deb1318b7f332dbb8e717c752ac7af48`. Source inventory, token generation, theme recipes, and focused tests are substantially implemented; browser visual acceptance is not complete.

### Current Integration Checkpoint

- The supplied offline Figma export resolves 9,981 nodes. All 343 exported token IDs, names, types, and mode values match the source.
- Token generation is deterministic; the ten converter tests pass, including alias cycles, cross-collection modes, units, and color parsing.
- Base and compact foundations, typography ratios, icon registry, and the currently mapped component recipes are composed into the Minim theme. Focused component, theme-build, and metadata tests pass for the declared scope.
- The documentation app resolves the local workspace core, not the published upstream package. The dependency lockfile is kept on the repository's pinned package manager.
- Input, selection, action, menu/spinner, Badge/Token, advanced-control, and content-family recipes have source-backed implementations. Rows below retain explicit out-of-source qualifications where core behavior exceeds the Figma axes; inline slot anatomy is recorded under its owning component rather than treated as a separate public recipe.
- Token converter tests, focused component tests, theme-build tests, TypeScript checks for the menu indicators, and knowledge validation have passed. Focused browser checks have passed for the explicitly recorded scope below; the full visual inventory remains pending and implementation evidence alone is not visual acceptance.
- No release, npm publication, or completed deployment is claimed at this checkpoint.

The authorized design evidence is Figma file `mHcauYaYWK3floQNsfolz6`, section `10633:55324` (`astryx`). Its current index contains 63 component sets, 1 standalone component, and 1,049 variants. Counts describe the design inventory only; they are not implementation counts.

## Constraints

1. Preserve Astryx behavior, public APIs, composition contracts, keyboard interaction, focus management, semantics, and accessibility behavior.
2. Add Minim semantic variables for the `base` and `compact` modes that actually exist in Figma. Do not create additional modes.
3. Treat Figma values as evidence to measure and map. Record unknown mappings as unknown until verified.
4. Add a glyph-font registry backed by [Minim Symbol](https://minim-symbol.sanjay0227.chatgpt.site/). Do not silently substitute unrelated icons or infer missing glyphs.
5. Apply component-level overrides only to exact, measured cases that cannot be represented by shared semantic variables.
6. Do not invent missing variants, props, states, behaviors, tokens, or component mappings.
7. Reuse the upstream generated documentation system and populate it from actual repository metadata. Do not maintain a parallel hand-written component catalog as a substitute.
8. Keep upstream license and attribution notices intact.

## Decision rules

- `Unknown` means no verified Astryx mapping has been recorded.
- `Pending measurement` means the Figma item exists in the index but has not passed measurement and review.
- A row may move to `Mapped` only when its Astryx owner, supported variants, and deviations are documented from code and Figma evidence.
- A row may move to `Implemented` only after its scoped code and tests exist. Visual similarity alone is insufficient.
- A row may move to `Validated` only after behavior, accessibility, and measured visual checks pass for the declared scope.
- Duplicate display names remain separate rows when their Figma node IDs differ.

## Tracking requirements

For each mapping decision, record the Figma node ID, relevant mode, measured values, Astryx package and component owner, supported variant intersection, required semantic variables, and any exact override. Unsupported or absent variants must remain explicitly out of scope.

Validation records must distinguish behavior/API compatibility, accessibility, visual measurement, generated documentation accuracy, and build/test execution. A passing result in one category must not be used to imply another.
